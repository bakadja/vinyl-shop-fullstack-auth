# SQLite → PostgreSQL migration

## Architecture and scope

Node.js 24 / Express 4 now use `pg` 8.23.1 and one bounded pool (maximum 5
connections per process). Single queries use `pool.query`; transactions use one
acquired client for BEGIN/COMMIT/ROLLBACK, with release in finally. Failed rollback
discards the client. Idle connection errors, authentication failures and CLI
failures log fixed diagnostics, never database URLs/passwords or raw database
errors. Graceful SIGTERM/SIGINT shutdown finishes in-flight HTTP work and ends the
pool. Session middleware, cookie settings, bcrypt cost, frontend rendering and
HTTP status/message contracts are unchanged.

No SQLite files are opened/imported automatically. Preserve/back up personal
SQLite databases outside Git yourself if needed. No accounts, carts or hashes are
seeded from them. Existing ignored SQLite files remain untouched. Historical
SQLite/security documentation remains as a record of earlier PRs. No Azure
resources, payments, Sentry, ruleset changes or auto-merge are included.

## Schema differences

| SQLite | PostgreSQL | Contract |
| --- | --- | --- |
| INTEGER PRIMARY KEY AUTOINCREMENT | INTEGER GENERATED BY DEFAULT AS IDENTITY | Numeric IDs; seeded product IDs 1–10 retained |
| REAL price | NUMERIC(10,2) | Exact stored cents; explicitly converted to finite JSON numbers |
| DATETIME created_at | TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP | Server timestamp; not exposed by existing API |
| Text names/passwords | TEXT with existing nullability | Bcrypt hash strings preserved verbatim |
| Optional per-connection FK enforcement | Always-enforced foreign keys | No orphan cart rows; restrictive deletion |
| No user/product cart constraint | UNIQUE(user_id, product_id) | Atomic concurrent quantity increments |
| Unique email/username | Unique email/username | Same case-sensitive account uniqueness |
| `?`/named parameters | `$1`, `$2`, … | No interpolation of user values |
| LIKE search | ILIKE search | Case-insensitive title/artist/genre search; exact genre selector |

`db/init.sql` retains all ten fictional albums, prices, stock and image paths.
Initialization takes a schema-specific transaction advisory lock, creates missing
tables, validates types/nullability/defaults and required constraints, then inserts
only missing seed IDs with ON CONFLICT DO NOTHING. Existing user, hash, cart and
edited catalogue rows survive repeat initialization. The product sequence is
aligned while holding a product-writer lock and a sequence DDL lock (reapplying
its unchanged cache setting), preventing concurrent allocations from being rewound. Incompatible schemas fail and roll back rather
than being silently accepted. This is initialization, not a general migration
framework for arbitrary pre-existing PostgreSQL schemas.

`cartItemId`/`totalItems` aliases are quoted. Prices and aggregate counts are
converted field by field, without global pg parser overrides. Invalid prices,
non-finite values and integers beyond Number.MAX_SAFE_INTEGER are rejected, never
silently rounded or returned as JSON strings/null. Only a null empty-cart SUM maps
to zero. Valid safe IDs above PostgreSQL int32 range retain missing-product 404 or
missing-cart-item 400 behavior. Registration handles both pre-existing accounts
and SQLSTATE 23505 races with the existing duplicate-account 400 response.

## Configuration (no required .env)

Supply DATABASE_URL or PGHOST, PGPORT, PGDATABASE, PGUSER and PGPASSWORD. URL
fields take precedence over PG connection fields. No credential has an application
default. PORT and SPIRAL_SESSION_SECRET retain existing behavior.

`npm start` and `npm run db:init` use Node 24's `--env-file-if-exists=.env`:
a missing file is allowed, and existing process environment values win. CI and
Azure can provide all values directly. `npm test` does **not** load `.env` or use
application connection defaults. `.env*` are ignored except `.env.example`.

TLS defaults to PGSSLMODE=verify-full and always sets rejectUnauthorized=true,
retaining hostname verification. Explicit PGSSLMODE=disable is allowed only for
loopback development, never NODE_ENV=production. Other SSL modes are rejected.
An optional PGSSLROOTCERT supplies a trusted CA file. A URL may include only
`sslmode=verify-full`, without a conflicting PGSSLMODE. Other URL options, including
SSL overrides and arbitrary connection options, are rejected. The URL is parsed
into explicit pool fields so pg's URL parser cannot replace the verified SSL
object. DATABASE_SCHEMA defaults to public; an explicit schema is one validated
identifier, never a comma-separated search path.

For Azure, provide the managed server's hostname/database/user/password through
environment variables, NODE_ENV=production and verified TLS, optionally its trusted
CA. Use the existing application's session configuration. Azure infrastructure
and actual Azure connectivity were not provisioned or tested; this PR does not
claim full production readiness of session storage or the application.

## macOS Apple Silicon / Colima / Docker

Install Node 24, Colima, Docker CLI and Compose through your normal tooling. For
Homebrew, `brew install colima docker docker-compose` provides a standalone
`docker-compose` binary. If `docker compose` is unavailable, substitute
`docker-compose` in the commands below; no user Docker configuration edit is needed.

```bash
colima start --profile vinyl-shop --cpu 2 --memory 2 --disk 20
# Inspect contexts, then explicitly select the new profile:
docker context ls
docker context use colima-vinyl-shop
cp .env.example .env
# Replace all password/session placeholders in .env locally before startup.
docker compose up -d --wait postgres
npm ci
npm run db:init
npm start
```

The development service binds to 127.0.0.1 and persists in the named
`postgres-data` volume. Its health check uses pg_isready. Repeat `npm run db:init`
as needed; it preserves existing data. `docker compose stop postgres` preserves
the volume, and `docker compose up -d --wait postgres` restarts it.

**Deliberate local reset deletes accounts, carts and catalogue edits.** Verify the
Docker context, Compose project and backups first. From that specific project's
root, `docker compose down --volumes` deletes its development volume; restarting
and running `npm run db:init` recreates a catalogue-only database. Never use reset
commands against a shared project or production server. No existing developer
volume was reset during implementation.

## Disposable tests: strict isolation

Simplest native setup on macOS:

```bash
brew install postgresql@17
npm ci
npm audit --audit-level=high
npm run test:postgres
```

The helper creates a new private mktemp cluster, generated SCRAM passwords and a
free loopback port; it never starts/reuses a Homebrew workstation service. It runs
`npm test`, stops the server on EXIT/INT/TERM and removes only its own temporary
directory. Set PG_TEST_BIN to PostgreSQL 17's binary directory if not using
Homebrew. Local Unix-socket bootstrap access is limited by the private directory;
TCP requires SCRAM. Bootstrap credentials are not provided to test processes.

Alternatively, the Compose `test` profile starts a **separate** PostgreSQL process
on port 15433 with disposable tmpfs storage and required external passwords:

```bash
# The optional local .env contains your chosen disposable test passwords.
docker compose --profile test up -d --wait postgres-test
# Explicitly export a TEST_DATABASE_URL using those restricted test credentials:
# postgresql://vinyl_shop_test:<your-test-password>@127.0.0.1:15433/vinyl_shop_test
npm test
# Stopping/recreating the disposable service discards its data:
docker compose --profile test stop postgres-test
docker compose --profile test rm -f postgres-test
```

Do not use the administrator password in TEST_DATABASE_URL. Compose interpolates
all services, so its configuration requires the example's development and test
variables even when starting one profile. Never print URLs/passwords in shared
logs. If using .env for Compose, export TEST_DATABASE_URL yourself: the test command
does not source application .env files.

Before test DDL, the harness requires an explicit loopback URL with port, exact
`vinyl_shop_test` database and restricted login, no URL options/fragment, no
application-target match (including loopback aliases), no privileged role flags or
role memberships, no database ownership or CREATE rights in public/control, and
an administrator-owned `vinyl_test_control.marker`. Naming or NODE_ENV alone is
insufficient. Bootstrap SQL must run **only on a newly created disposable server**;
never use it to relabel a development/production database.

Each fixture creates one UUID schema and records its OID/owner. Every pool/HTTP
subprocess receives an explicit single-schema search path with no public fallback.
Children stop before teardown. Cleanup rechecks server identity, then calls a
bootstrap-admin-owned helper with a pinned search_path and restricted EXECUTE.
The helper locks the disposable database's pg_namespace catalog before checking
recorded name/OID/owner and dropping the schema, preventing rename/recreation
between verification and deletion. It accepts only the restricted test session
and exact fixture-name pattern; it cannot target public/control or a forged
identity. No general administrator credentials or catalog-locking rights are
granted to tests. Cleanup never executes DROP DATABASE or an application-wide reset. Privileges protect public
and marker objects. Missing/unsafe configuration is a failure, never a skip.

## Tests and CI

The 57 baseline behavioral tests remain, including unchanged DOM XSS and frontend
regression files. Added coverage includes strict target/cleanup guards, explicit
numeric conversion, TLS config, connection refusal, schema/constraints,
concurrent/idempotent initialization, rollback/client reuse, mixed-case filtering,
duplicate registrations, larger concurrent carts/user isolation, int32/unsafe
aggregate boundaries, graceful in-flight shutdown, and optional/environment-only
CLI configuration.

SQLite-specific adaptations (no HTTP/UI assertions removed):

1. Five database fixtures use guarded PostgreSQL schemas instead of local files.
2. sqlite_master/PRAGMA integrity/FK checks become PostgreSQL metadata/validated
   constraints plus real FK rejection tests.
3. `?`, lastID and SQLite result shapes become `$n`, RETURNING and pg rows/rowCount;
   raw test COUNT values receive explicit safe conversion.
4. The EEXIST/file-byte comparison test becomes repeat initialization with complete
   before/after row snapshots, including an edited product, synthetic hash and cart.
5. CLI initialization uses an explicit isolated schema and tests no-.env operation;
   catalogue, empty-account/cart and image/filter assertions remain.

Linux `test` runs PostgreSQL 17 as a loopback-mapped GitHub service. A disposable
service credential comes from the CI run's ID/attempt (not a production secret);
bootstrap creates a randomly generated, masked restricted test password. macOS
`test-macos` installs postgresql@17 and uses the same native helper. Both keep
Node 24, read-only workflow permissions, persist-credentials=false, locked
installation and npm audit --audit-level=high. Neither skips PostgreSQL tests.
External `SonarCloud Code Analysis` remains mandatory and unchanged.

## Plan deviations and execution rulings

- Reused the supplied checkout on the new requested feature branch rather than
  moving unrelated existing security worktrees; untracked .DS_Store files preserved.
- Installed missing local PostgreSQL/Colima/Docker tooling; no host PostgreSQL service
  was started and no existing personal database was used.
- Retained the SQLite export during intermediate query commits, then removed it
  after PostgreSQL functionality passed. Intermediate auth tests depending on cart
  endpoints were verified with all original assertions once Task 5 migrated carts.
- Added a separate Compose test profile/instance and admin-owned marker to enforce
  the approved strict isolation requirement, rather than trusting a test DB name.
- Used standalone Homebrew docker-compose during verification without modifying
  Docker plugin configuration. CI bootstrap credentials are run-specific values;
  restricted test credentials are generated, not hardcoded.
- Independent review found encoded application-target comparison, a namespace
  replacement race and a sequence-alignment race. Added canonical target
  comparison, locked server-side test cleanup and serialized sequence alignment,
  with real interleaving/allocator regressions. The original cleanup and missing
  sequence lock were each proven unsafe by regression mutation runs.
- Optional .env loading is explicit and tests never source it. No API/session/UI
  redesign or automatic personal-data migration was introduced.

Implementation proceeded natively in Tasks 0–8 order after separate design and
plan approval. Review findings and remote-check results are reported in the draft
PR; no merge or auto-merge is authorized.

reported findings without suppressing rules:

| databaseConfig S3776 (complexity 23) | Extract URL/TLS-option parsing, connection validation and verified-TLS construction into focused private helpers |

Test schema creation and identity lookup now use one PostgreSQL transaction. A
failed lookup or missing identity rolls back CREATE SCHEMA; the cleanup hook is
still registered before setup, and the cleanup identity is published only after
commit. The restricted test role, server checks, exact namespace OID/owner and
protected cleanup function are unchanged. No DROP DATABASE or broader cleanup
permission is introduced.

Five regressions were added: failed identity query, empty identity result,
sanitized login connection refusal, sanitized current-user connection refusal,
and native startup failure cleaning temporary paths containing spaces. The two
schema tests interpose only at the pg driver boundary and inspect real PostgreSQL
catalogs; both fail against the previous implementation. Original assertions,
including DOM XSS, TLS/numeric checks, authentication, carts/concurrency,
initialization/sequence safety and graceful shutdown, remain in place.

Local `npm ci` and `npm audit --audit-level=high` pass (0 vulnerabilities). The
complete native PostgreSQL `npm test` run passes **88 tests**, 0 failures/skips.
Final Linux/macOS CI and Sonar results for the correction commit are recorded in
